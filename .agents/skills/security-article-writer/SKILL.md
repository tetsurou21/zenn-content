# Security Article Writer（脆弱性・セキュリティインシデント記事作成スキル）

Zenn向けの「脆弱性（CVE等）の技術解説記事」および「セキュリティインシデント分析記事」を、正確な一次情報とわかりやすい図解（Mermaid）・Zenn記法を用いて執筆するためのワークフローです。

---

## ワークフロー手順

### Step 1: 記事タイプとターゲットの確認

ユーザーの依頼内容から、以下のどのパターンで執筆するか判断します（不明確な場合はユーザーに確認します）。

1. **パターンA：脆弱性（CVE等）の技術解説記事**
   - 特定のソフトウェアやライブラリの脆弱性（CVE-XXXX-YYYYなど）について、影響範囲、技術的な原因、攻撃の仕組み、修正パッチ（diff）、対策を解説する。
2. **パターンB：セキュリティインシデント分析記事**
   - 実際に発生した不正アクセスや情報漏洩、サプライチェーン攻撃などの事案について、発生経緯（タイムライン）、侵入経路・原因、被害範囲、今後の対策・教訓を解説する。
3. **パターンC：複合型（脆弱性＋悪用インシデント）**
   - 特定の脆弱性が実際に悪用されたインシデントについて、脆弱性の仕組みとインシデントの経緯の両方を解説する。

各パターンの詳細な構成案は [記事テンプレート集](./references/templates.md) を参照してください。

---

### Step 2: 一次情報の調査とファクトチェック

記事を執筆する前に、`search_web` 等で候補となる一次情報を探した上で、**必ず各URLの実ページを直接取得（フェッチ）して本文を読み込み**、事実関係を裏付けします。

#### 一次情報URLの実ページ取得と検証ルール（必須）
- **`search_web` の要約だけで記事や出典を書かない**:
  - `search_web` の検索結果サマリーは複数の記事（例：第1報〜第N報）の内容が混ざっていたり、URLが `vertexaisearch.cloud.google.com/grounding-api-redirect/...` のリダイレクトURLになっていたりすることがある。
  - **URLを推測・補完して記載することは厳禁**（例：Microsoft Learn等のドキュメントURLのスラッグを知識や推測で生成すると404リンク切れの原因になる）。
- **全出典URLのHTTPステータス・タイトル・本文テキストの直接取得**:
  - 記事の出典（`[ref-1]`〜`[ref-N]`）として採用するすべてのURLについて、`curl` または Python スクリプト（サンドボックス内で外部通信がブロックされる場合は、標準サンドボックスで試行後に `BypassSandbox: true` を用いて実行）により、以下を必ず実行する：
    1. リダイレクト解決後の最終URLとHTTPステータスコード（`200 OK` であること）を確認する。
    2. ページの `<title>` / `<h1>` と**本文テキスト全文**を取得し、スクラッチファイル等に保存して内容を確認する。
    3. ポインターページ（例：「詳細は別サイトのお知らせをご覧ください」とだけ書かれた案内ページ）ではなく、**具体的な数値・日時・事実が実際にある大元の一次情報ページ**を出典URLとして採用する。
    4. 続報形式（第1報〜第N報）のインシデントでは、各報の公表日時と「どの事実・数値・タイムラインが第何報に記載されているか」を1報ずつ照合し、可能な限り `[ref-1]`＝第1報、`[ref-2]`＝第2報…のように番号と報数が対応するよう整理する。

#### 参照すべき一次情報源（これ以外の二次情報は引用・参照しない）
- **脆弱性データベース**: NVD (NIST)、CVE.org、JVN / JVN iPedia、OSV (Open Source Vulnerabilities)
- **ベンダー・ディストリビューション・クラウド公式情報**:
  - GitHub Security Advisories (GHSA)、公式セキュリティアドバイザリ、リリースノート
  - Linuxディストリビューション公式トラッカー（Red Hat CVE Portal、Ubuntu Security、Debian Security Tracker、SUSE Security等）
  - クラウドプロバイダー公式アドバイザリ（AWS Security Bulletins / ALAS、Microsoft MSRC、Google Cloud Security Bulletins等）
  - 修正コミット（Commit diff）およびPull Request
- **公的機関・発見者自身の一次レポート**: IPA（情報処理推進機構）、JPCERT/CC、CISA、脆弱性発見者（リサーチャー・セキュリティベンダー）によるオリジナルの研究発表、当事者企業が公表した公式調査報告書（プレスリリース）・経営陣の公式発信
- **主要報道機関・専門メディアによる取材記事（インシデント分析における捜査動向・記者会見・専門家見解）**:
  - 特定企業のセキュリティインシデント分析（パターンB）において、企業のプレスリリースだけでは公表されない**捜査機関（警察・省庁等）の動向、記者会見での質疑応答、またはセキュリティ専門家・元捜査幹部による犯人像・手口の分析**を記載する場合は、全国紙（日本経済新聞、読売新聞、毎日新聞、朝日新聞等）、放送局（NHK、FNN、テレビ朝日系等）、通信社（時事通信、共同通信等）、または主要IT専門メディア（Impress Watch / INTERNET Watch、ITmedia等）の取材記事を出典として参照してよい。その際も「誰の発言・どの報道機関の報道か」を明記し、必ず上記「URLの実在確認と本文の直接取得」の手順で実在（`200 OK`）と記述の一致を検証すること。
- **【禁止事項】個人ブログ・まとめサイト等の不確実な二次情報の参照禁止**:
  - Qiita、Zenn、note、個人ブログ、まとめサイト等の不確実な二次情報は情報源・出典として参照・記載してはならない。

#### 調査・記載の鉄則
- **事実と推測の分離・主張主体の明確化**:
  - 公式に発表されている「事実」と、技術的な状況から導かれる「推測・考察」を明確に書き分ける（推測を含む場合は「〜と考えられる」「公式発表では明言されていないが〜」と明記する）。
  - 深刻度や影響（特にRCE等の重大な影響）について、NVD/ベンダーの公式見解（例：DoS）と特定のリサーチャー・発見者の主張（例：「RCEを実証したと主張しているのは〇〇社であり、かつ△△の環境に限られる」）がある場合は、**誰の主張か・どの前提条件に限定されるか**を正確に切り分けて記載する。
- **記事パターンに応じた構成の最適化（不要な節の排除と重複防止）**:
  - **パターンA（OSS・OS・ソフトウェアの脆弱性解説）や広く配布されているパッケージ・証明書の危殆化事案**では、読者が自身の環境を点検・対処する必要があるため、影響バージョン一覧とは別に **`## 影響を受ける条件`**（①ネットワーク・インフラ構成の前提、②通常使われない機能・プロトコル仕様の補足説明、③自環境の確認コマンド）および **`## 対策と緩和策`** の節を設け、他の節と説明が重複しないように集約する。
  - **パターンB（特定企業・特定Webサービスにおける不正アクセス・情報漏洩等のインシデント分析）**では、すでに特定事業者の環境で発生・サービス停止等に至った事案であり、一般読者が自環境の確認コマンドや設定変更を行う性質のものではないため、**形骸化した `## 影響を受ける条件` や `## 対応と緩和策` の節は設けない**。代わりに以下の構成に集中し、同じ説明が複数箇所に分散・重複しないように整理する：
    1. **`## 概要`**（事案の概要、主な被害・影響、運営会社の対応状況）
    2. **`## 被害・影響範囲と運営会社の対応施策`**（影響範囲サマリー表、補償・救済措置・懸賞金等の施策一覧表）
    3. **`## インシデントの時系列`**
    4. **`## 攻撃の手口と被害構造の分析`**（侵入経路と被害波及の図解、なぜその被害につながったかの技術的・構造的要因）
    5. **`## 攻撃者（犯人）に関する公表情報と特定に向けた動き`**（脅迫内容・要求額、犯人サイトの動向、捜査・特定に向けた動きなど）
- **バージョン番号・識別子の正確性と明確化**:
  - **影響を受けるバージョン（Affected versions）**と**対応状況（修正バージョン等）**を系統ごとに明確に対比して記載する（「〜以降の幅広いバージョン」のような曖昧な表現だけで済ませない）。
  - **テーブルの「修正版」列の記載ルール**:
    - 「修正版」列はひと目でバージョンまたはステータスがわかるよう、**`x.y.z`**（バージョン番号のみ）、**`準備中`**、**`対応しない`**、**`不明`** のように簡潔に記載し、詳細な条件・アドバイザリ番号・必要なアクションなどの補足事項は別の **「補足」列** に分けて記載する。
  - **LinuxカーネルやOS関連パッケージの脆弱性の場合**は、必ず以下の**両方**を分けて明記する：
    1. **Upstream（Linuxカーネル本体やアップストリームOSS）の系統別影響バージョンと修正版**
    2. **主要Linuxディストリビューション（Ubuntu, Debian, RHEL, Amazon Linux, SUSE等）における対象リリースと修正版**
  - **クラウド環境に影響がある脆弱性・インシデントの場合**は、必ず**主要クラウドプロバイダー（AWS, Microsoft Azure, Google Cloud / GCP）の対応状況**も同様のテーブル形式（「修正版」列＋「補足」列）で記載する。
- **出典の明確な紐づけ（どの情報がどのリンクから得られたかの可視化）**:
  - 記事末尾にリンクを並べるだけでなく、「どの数値・事実・緩和策がどの情報源（URL）から得られたものか」が1対1で追跡できるようにする。
  - **表記ルール（`[1:1]` のような枝番を出さず `[1]` のみに統一）**:
    - Zennの脚注記法（`[^1]`）を使うと、複数回参照した際に `[1:1]`, `[1:2]` のような枝番が自動付与されてしまうため、**`[^1]` 記法は使用しない**。
    - 代わりに、Markdownの参照リンク記法 **`[[1]][ref-1]`** を使用し、記事末尾の「参考資料・出典一覧」セクションの番号付きリスト（`1. [出典名][ref-1]`）と対応させる（「本文中の [1]〜[N] は〜に対応している」といった説明文は入れず、番号付きリストのみをシンプルに並べる）。
    - **テーブル（表）内**：「出典 / 情報源」専用の列は作らず、**他の列の適切な箇所（補足列の末尾など）に直接 `[[1]][ref-1]` の番号リンクを貼る**。同じ行の複数のセルに同じ出典リンクを重複して貼らず、行末（補足列など）にまとめて1回だけ記載する。
    - **本文（文章・箇条書き）内**：文章中の事実・記述に対して `[[1]][ref-1]` のように番号リンクを付与する。ただし、**同じ節・段落・同じ箇条書きブロックの中で近接して同じ出典リンクを何度も繰り返し貼ると冗長になるため、段落や箇条書きのまとまりごとに代表箇所（末尾など）へまとめて付与する**こと。また、1箇所に複数の同じ内容の出典を過剰に並べないこと。
    - **引用事実と技術的考察の厳密な切り分け（誤帰属の防止）**：`[[1]][ref-1]` を付与した文・箇条書き・表のセルには、**実際に `[ref-1]` のページ内に書かれている事実・数値・日時・手順のみ**を含めること。一般的なプロトコル仕様や筆者による技術的考察・背景説明の文に、それらが書かれていないインシデント発表等の出典番号を付与してはならない（文を分けるか、該当する仕様書の出典のみを付与する）。

### Step 3: Zenn記事ファイルの準備

新規記事を作成する場合は、Zenn CLI またはファイル作成によって `articles/` 配下にMarkdownファイルを用意します。

1. スラッグ（`slug`）の決定：
   - 12〜50文字の半角英数字・ハイフン・アンダースコア（例: `cve-2026-xxxx-analysis` や `xxxx-security-incident-summary`）
2. ファイル生成コマンド：
   ```bash
   npx zenn new:article --slug <決定したスラッグ> --title "<記事タイトル>" --type tech --emoji "🛡️" --published false
   ```
   ※ 既存の記事ファイルを編集する場合はそのファイルを対象とします。
3. Frontmatterの設定：
   - `title`: 脆弱性名/CVE番号やインシデント対象、記事の要旨がひと目でわかるタイトル
   - `emoji`: セキュリティ系に適した絵文字（`🛡️`, `🔒`, `⚠️`, `🔍`, `🚨` など）
   - `type`: `"tech"`
   - `topics`: 関連する技術タグを最大5つ（例: `["security", "cve", "web", "linux", "nodejs"]`）
   - `published`: 原則 `false`（下書き状態）で作成する

### Step 4: 執筆・図解（Mermaid）・Zenn記法の適用

[記事テンプレート集](./references/templates.md) と [Zenn記法・Mermaid図解ガイド](./references/zenn-conventions.md) を読み込み、記事本文を執筆します。

#### 執筆時の必須ポイント
1. **文体（トーン＆マナー）と誇張表現の排除**:
   - 記事本文の文体はですます調（敬体）ではなく、**「〜だ」「〜である」調（常体）**で統一する。
   - 箇条書きや図表内、注意喚起ボックス（`:::message`）内も原則として常体または体言止めで統一し、ですます調が混在しないようにする。
   - **大げさな表現・情緒的な修飾語を使用しない**：「わずか〇時間後」「痛恨の〜」「壊滅的な〜」「驚くべきことに」「〜に過ぎなかった」「危険！」などの誇張表現・扇情的な表現・感嘆符（`!`）は排除し、事実と数値を客観的かつ淡々と記述する。
2. **冒頭のサマリー**:
   - 記事の冒頭で「何についての記事か」「誰が影響を受けるか」「今すぐ何をすべきか（結論）」を簡潔にまとめる。
   - 「本記事は脆弱性の技術的な仕組みの理解と適切な防御・対策を目的としている。管理権限を持たないシステムに対する検証や悪用は法律により禁じられている。」といった定型の免責事項・悪用厳禁の注意書きは記載しない。
   - 調査進行中である旨の注記や、特に重要な技術的警告がある場合にのみ Zenn の `:::message` または `:::message alert` を活用する。
3. **Mermaidによる視覚化**:
   - 複雑な攻撃シーケンス、認証バイパスの流れ、サプライチェーンの侵害経路などは、Mermaid（`sequenceDiagram` や `flowchart TD/LR`）を用いて最低1つは図解を入れる。
4. **コード差分（diff）の活用**:
   - OSSの脆弱性などで修正コミットが公開されている場合は、` ```diff <言語> ` ブロックを使って「なぜ脆弱だったのか」「どう修正されたのか」を視覚的に解説する。

### Step 5: セルフレビューと検証

執筆完了後、ユーザーに報告する前に以下の項目を必ずセルフチェックしてください。

- [ ] **全出典URLの疎通確認（HTTP 200）と本文との1対1照合**:
  - 記事末尾のすべての `[ref-k]` URLに対してスクリプト等で実アクセスを行い、リンク切れ（404等）やアクセス拒否（Bugzilla等のHTTP 200 `Access Denied` を含む）、別ページへの意図しないリダイレクトが1件もないことを機械的に検証したか。
  - 本文・表内のすべての `[[k]][ref-k]` について、**その文やセルに書かれている具体的な数値・日時・固有名詞・手順が、リンク先 `[ref-k]` の実ページ本文に文字通り記載されているか**を1箇所ずつ照合したか（第N報の取り違え、概要ページと詳細ページの取り違え、筆者の技術的考察への誤った出典付与がないか）。
- [ ] **影響を受けるバージョン・修正バージョンの正確性**: Upstream（EOL系統を含む）・各ディストリビューション・主要クラウドプロバイダー（AWS, Azure, GCP）における影響バージョンと修正バージョンに抜け漏れや最新情報との乖離がないか。
- [ ] **影響確認用コマンド・緩和策コマンドの正確性**: 記載した確認コマンド（例：`ss`、`sysctl`、`uname` 等）のオプション挙動（フラグの組み合わせによるフィルタ条件や `sudo` の要否など）およびファイアウォール設定等が実際に意図通り動作するか。
- [ ] **技術的な説明の正確性**: 脆弱性の発生メカニズム（競合状態の時系列・ロック／RCUの挙動・ポインタのライフサイクル等）とシーケンス図・修正パッチ（Diff）の説明に矛盾や論理的な飛躍がないか。
- [ ] **文体とフォーマット**:
  - 文体が「〜だ」「〜である」調（常体）で統一されており、ですます調が混ざっていないか。
  - 「わずか〜」「痛恨の〜」「壊滅的な〜」などの大げさな表現や情緒的な修飾語、感嘆符（`!`）が含まれていないか。
  - 本文・表の各記述に `[[1]][ref-1]` 形式の参照リンクが付与されており（`[^1]` による `[1:1]` のような枝番を出していないか）、同じ表の行内や近接する箇条書き・段落内で同じ参照リンクが冗長に重複していないか、かつ出典がすべて公式の一次情報のみになっているか。
  - Mermaidブロック内のノードラベルに括弧 `()` `[]` などの特殊文字が含まれる場合、ダブルクォーテーション `""` で囲まれているか（構文エラー防止）。
  - **太字（`**...**`）と全角記号の隣接によるパース崩れがないか**: CommonMark（Zennの `zenn-markdown-html`）の仕様上、`には**「...」**と` や `後の**...（テイクダウン）**が` のように、`**` の内側先頭・末尾に全角括弧類（`「` `」` `（` `）` `【` `】`）があり、かつ外側にスペースなしで日本語文字が隣接すると太字として認識されず `**` がそのまま表示される。引用や括弧を太字にする際は必ず **`「**...**」`** や **`**...**（...）`** のように括弧類を `**` の外側に配置し、変換後のHTMLに未パースの `**` が残っていないことを確認すること。
